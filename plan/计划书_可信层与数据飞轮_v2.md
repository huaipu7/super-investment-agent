## 一、问题诊断（基于代码核查，非推测）

先说明诊断方法：以下结论来自逐文件阅读 `app/`、`scripts/`、`api/`、`ui/`，每条都带 `文件:行`。凡未能核实的，标为「未核实」，不写估计值。

### 1.1 现状盘点（真实数字）

| 维度 | 现状 |
|---|---|
| 测试脚本 | `scripts/` 共 **59** 个 `.py`：`verify_*` **36**、`smoke_*` **11**、`eval_*` **4**、`test_e2e` **1**、`run_*` **3** |

### 1.2 六个真实缺口（这是本方案的靶子）

**缺口 1｜研究产物的质量完全没有被评测**
`verify_investigation.py` 的 161 个断言测的是**机制**（预算、状态机、归因拒绝），不是**内容质量**。深度研究报告写得对不对、数字有没有编，无人过问。`eval_groundedness.py` 只覆盖报价报告这一条最窄的路径。

**缺口 2｜数字来源在数据里不可区分**
`app/analysis/pipeline.py:668-690` 返回的 `result` 是个大嵌套字典，**没有任何字段标明某个数字是代码算的、数据源拿的、还是模型编的**。而报告渲染器 `app/report/markdown.py` 对所有字段一视同仁地渲染。这是幻觉治理的结构性根因。

**缺口 3｜三处降级被伪装成正常内容**（已逐行确认）
- `app/analysis/swot.py:561-571` `_empty_swot()` 在 LLM 失败时返回 `"rating": "中性"` —— **一个伪造的评级结论**，会被 `markdown.py:146` 渲染成「SWOT 综合评级」。
- `app/analysis/segment.py:371` `_default_segment()` 伪造 100% 占比的「综合业务」分部，**且该结果会进入 `compute_sotp()` 参与估值**（`segment.py:263`）。
- `app/analysis/news.py` LLM 失败时仍置 `available=True`。
- 共同根因：`app/llm/structured.py:74-90` 的 `parse_llm_json` 解析失败只 `logger.warning`，调用方拿不到「我降级了」这个信号。

**缺口 4｜模型产出的数字未被约束**
分部占比 `revenue_share` / `net_income_share`（`app/analysis/segment.py:247-254` 只做归一化，不校验真伪）与新闻情绪分直接由 LLM 给出，并流入 SOTP 估值。所以「所有数字都是代码计算的」这个说法**对分部估值不成立**。

**缺口 5｜插补不可见**
`app/data/cleaning/missing_handler.py` 对训练类数据做前向填充/中位数插补（`:37/57/78`），但插补次数从不进入报告。读者无法区分「这个毛利率是财报披露的」和「这个毛利率是填出来的」。

**缺口 6｜飞轮断在第一个环节**
数据飞轮五个环节：使用 → 日志 → 标注 → 评测 → 改进。当前：日志有（`audit.db`），但**采集不可得**——没有任何反馈信号，所以后面四个环节全部无法启动。这不是「飞轮转得慢」，是**飞轮根本没接上**。

### 1.3 一个被忽略的资产

`data/phase5_full_aapl.json` 是一份真实的完整管线产物（34 KB，251 个数值叶子）。这意味着：**绝大多数质量评测可以跑在设计时保存的真实产物上，不需要每次重新调用 LLM**。这条决定了整个评测架构——见 §3.2。

## 二、核心设计：事实台账（Fact Ledger）

只做一件事，但它同时是评测、治理、飞轮三条线的地基。

### 2.1 做法

给每次管线运行产出一份**带出处的事实清单**：

```json
{
  "run_id": "800a1f3c9d24",
  "ticker": "600519.SS",
  "git_sha": "d0fc617",
  "model": "deepseek-v4-flash",
  "facts": [
    {"fact_id": "F001", "path": "financial_analysis.ratios.roe",
     "metric": "ROE", "value": 0.3365, "unit": "ratio",
     "as_of": "2023-12-31", "provenance": "computed",
     "module": "analysis.financial", "evidence_ref": null},
    {"fact_id": "F117", "path": "sotp_analysis.segments[0].revenue_share",
     "metric": "分部营收占比", "value": 0.62, "unit": "ratio",
     "as_of": null, "provenance": "llm",
     "module": "analysis.segment", "evidence_ref": null},
    {"fact_id": "F204", "path": "financial_analysis.ratios.gross_margin",
     "metric": "毛利率", "value": 0.9102, "unit": "ratio",
     "as_of": "2020-12-31", "provenance": "imputed",
     "module": "data.cleaning.missing_handler", "evidence_ref": "forward_fill"}
  ]
}
```

出处（`provenance`）只有五种，没有第六种：
`computed`（纯 Python 计算）｜`source`（外部数据源原值）｜`llm`（模型产出）｜`imputed`（插补/填充）｜`degraded`（降级占位）。

### 2.2 关键机制：未分类即失败

出处的判定不靠每个模块自己声明（那要改几十个文件、且必然漏），而是靠**一张路径→出处的映射表** `app/trust/provenance.py`：

| 路径模式 | 出处 |
|---|---|
| `financial_analysis.*`、`valuation_analysis.*`、`trade_plan.*` | `computed` |
| `company_info.*`、`*_analysis.*.source` | `source` |
| `sotp_analysis.segments[*].{revenue_share,net_income_share}` | `llm` |
| `news_analysis.sentiment_score` | `llm` |
| `swot_analysis.{summary,rating}`、`competitive..summary`、`geopolitical..transmission_path` | `llm` |
| `*.imputed = true` | `imputed` |
| `*.degraded = true` | `degraded` |
| **匹配不上任何模式** | **`unknown`** |

`unknown` 在 L0 评测里**直接判失败**。于是：以后谁在 `result` 里加一个新字段却忘了归类，评测立刻报错。——映射表不会腐化，因为评测替它守门。

### 2.3 为什么这是地基

| 问题 | 没有台账 | 有台账 |
|---|---|---|
| 模型有没有编数字？ | 主观判断 | 可数比率：`llm` 字段里的数字能归因到 `computed/source` 的比例 |
| 报告里的数可信吗？ | 只能信模板 | 每个数都能追到出处与期间 |
| 飞轮该标什么？ | 整篇回复 | 精确到 `fact_id`：「这条占比不对」 |
| 回归基线存什么？ | 整份 JSON 全文 diff | 指标化的台账指标，可比、可告警 |
| PRD 的验收标准怎么挂钩？ | 空泛 | 「本需求验收：L1 接地率 = 1.0」 |

## 三、四条工作流

### 3.1 W1｜幻觉治理：三道闸门 → 四道闸门

现有三道闸门是真实的，本方案不推翻，只补齐：
1. 确定性计算边界（`analysis/financial.py`、`valuation.py`、`expert_scoring.py` 等纯 Python）— **保留**
2. 结构化解析 + pydantic 校验 + 兜底（`llm/structured.py`、`llm/schemas.py`）— **保留但去静默**
3. 调查模块证据闸门（`investigation/loop.py:482-487` 要求 `source_ref` 逐字出现在工具结果中）— **保留**

#### 新增：闸门 4 —— 数值接地（Numeric Grounding）

`app/trust/grounding.py`：

```
对 result 中所有 provenance == "llm" 的字符串字段
  → 抽取数字 token（含中文数量级：亿/万/百分比/pp/bps）
  → 每个数字必须在台账中找到来源事实：
       · 数值相等（按显示位数容差）
       · 单位可换算（0.62 ↔ 62% ↔ 62.0）
       · 期间不冲突（若文中出现年份，须与事实 as_of 一致）
  → 输出 GroundingReport{checked, matched, unmatched:[{span,value,field}], rate}
```

**与现有 `eval_groundedness.py` 的关系**：那个脚本是这件事的 1 个 fixture 特例（`scripts/eval_groundedness.py:77-124`），且只覆盖报价路径。本方案把它**一般化**为全管线能力，脚本保留作为 L1 的最小用例，反向控制（伪造 99.99%）机制直接继承。

**生产化**：接地检查同时以**运行时护栏**形式挂在 `pipeline.py` 出口，结果写入台账与 metrics（`grounding_rate`），不阻断主流程——因为本地单用户场景下，阻断会让用户拿不到报告；但比率下降必须可见。

#### 修补 A：降级必须显式

| 位置 | 现在 | 改为 |
|---|---|---|
| `swot.py:561` `_empty_swot` | `rating: "中性"` | `degraded: True, degraded_reason: "LLM 解析失败"`；`rating` 置 `None` |
| `markdown.py:144-146` | 渲染「SWOT 综合评级: 中性」 | 渲染「SWOT 综合评级：未生成（LLM 解析失败）」 |
| `segment.py:371` `_default_segment` | 伪造 100% 「综合业务」 | 返回 `degraded: True`；**`compute_sotp` 遇降级分部时返回 `sotp_value_*: None`**，不拿假占比算估值 |
| `news.py` 失败分支 | `available=True` | `available=False, reason=...` |
| `llm/structured.py:74-90` | 静默 `warning` | 仍返回 default，但**同时返回 `degraded` 标记**；调用方可感知 |

**开关**：新增 `TRUST_STRICT_MODE`（`app/config.py`），默认**开启**。关闭时退回现有行为，供对照演示。开这个开关会改变现有报告的可见输出——这是有意的，但需要跑全量回归确认没有别处依赖「中性」这个值。

#### 修补 B：插补可追溯

`missing_handler` 记录插补计数与字段名 → 进台账（`provenance=imputed`）→ 报告末尾「数据说明」区块显示：「本页 3 项财务指标为插补值（前向填充 2 / 中位数 1）」。

#### 修补 C：不可验证的出处显式标注

SWOT 的 `source`、新闻的 `evidence`、地缘政治的 `probability` 目前是自由字符串直出（`markdown.py:410-486, 553`）。方案：不假装能验证，而是在渲染时加统一后缀标记「模型推断」——**区分「有出处」与「模型说的」这件事本身，就是治理**。

#### 明确不做
- **不引入第二个 LLM 做「事实性裁判」**。理由：不可验证（裁判也会错）、有成本、且会让「幻觉治理」变成「两个幻觉互相打分」。
- 不重写提示词工程。

### 3.2 W2｜评测：五层，离线优先

#### 架构决定（本方案最重要的一条）

**L0–L3 全部跑在已保存的真实产物上，零 LLM 调用、可重复、秒级。**

依据：`data/phase5_full_aapl.json` 证明真实产物可以持久化。所以把「跑管线」和「评管线」拆开：

```
                    ┌── 采集（贵）──┐        ┌── 评测（便宜）──┐
  真实标的 ──▶ 跑一次管线 ──▶ data/artifacts/{ticker}/{ts}.json ──▶ L0/L1/L3
                                                                  └──▶ baseline 对比
```

采集可能几小时一次，评测可以每次改代码都跑。这是把「评测」从一次性演示变成工程习惯的唯一办法。

#### 五层定义

| 层 | 名称 | 测什么 | 成本 | 通过门槛 |
|---|---|---|---|---|
| **L0** | 台账闭合 | 每个数值路径都有出处；无 `unknown`；`degraded` 必带 reason；`None` 未被渲染成非「—」 | 零 | 违规数 = 0 |
| **L1** | 数值接地 | `llm` 字段中数字的归因率；含伪造 99.99% 反向控制 | 零 | rate = 1.0 且控制被检出 |
| **L2** | 检索质量 | nDCG@k / Recall@k / MRR | 零（离线检索） | nDCG@4 ≥ 0.5（沿用现阈值） |
| **L3** | 生成质量 | **规则即断言**清单（见下） | 零 | 全部硬项通过 |
| **L4** | 端到端 | 3 支真实标的跑全链路：成功/降级/token/耗时 | 真实 LLM，约 3 × 150s | 成功率 3/3，降级 0 |

#### L3「规则即断言」为什么不用自由打分

自由式 LLM-as-judge 打分（「请给这份报告打 1-10 分」）在本项目里**不可用**：分数不可复现、无法归因、且无法纳入回归。改用**确定性断言清单**，每条都能直接看出「哪条不过、哪一行」：

1. 期间一致性：文中「2023 年」的数字，必须来自 `as_of` 为 2023 的事实
2. 竞争对真实性：竞品名必须出现在真实数据源返回的列表里（扩展现有 `analysis/validator.py:239` 的 difflib 校验）
3. DCF 敏感性单调性：折现率↑ → 估值↓，必须单调（纯计算可验）
4. 分部占比自洽：SOTP 各分部占比之和 = 1（容差 1e-6），且若任一分部为 `llm` 来源，报告必须标注「分部占比为模型估计」
5. 措辞红线：禁止「保证/必然/一定会/稳赚」类确定性表述（扩展 `compliance/rules.py:23`）
6. 空节检测：任何章节若内容为空或为占位，必须显式标「未生成」，不得留白

**可选**：对**语气/可读性**允许一次采样式 LLM 打分，仅作参考、不进回归门槛。事实性一律走 1–6。

#### L2 扩样的诚实处理

现状 4 文档 / 3 查询，不具代表性。扩样方案必须解决「相关性标注从哪来」——**这里绝不能编造标注**：

- 方案 A（首选）：从 `data/knowledge_db/` 抽取**真实入库文档**，由用户人工标注相关性（3 档：完全不相关/部分/高度相关）。工作量约 30 分钟，产出 20–30 条查询的标注集，可声明为**人工标注**。
- 方案 B（退路）：用明确规则构造弱监督标注（如「查询中的 ticker 与文档 metadata.ticker 一致 → 相关」），**必须声明为弱监督、不声称等同人工标注**。
- 若两者都不做，则维持现状，并在文档里如实写明「检索评测仅为烟囱测试，不构成质量结论」。

#### 回归基线

`data/eval/baseline.json`：存每层指标的当前值 + 允许漂移容差 + 记录时的 `git_sha` / `model` / 产物哈希。
`scripts/run_eval.py --baseline` 对比并报警，解决「数字会变但没人知道」的问题。

#### Runner 改造

现有 `scripts/run_eval.py` 只聚合 3 个 D3 评测、只打印文本、无 JSON、失败细节不输出（`:22-52`）。改为：

```
run_eval.py --tier l0,l1,l2,l3     # 默认 l0-l3（全离线）
           --tier all              # 含 L4（真实 LLM，需确认）
           --json                  # 写 data/eval/latest.json
           --baseline              # 与 baseline 对比，超漂移即失败
```

不引入 pytest/CI 框架——理由见 §6。

### 3.3 W3｜数据飞轮：把第一个断点接上

#### 现状

日志有（`data/audit.db`，append-only，带 `request_id`），但**没有任何反馈信号**。所以五环里第 1 环（使用）没有产生可学习的数据，后面全部空转。

#### 最小可行闭环（六件套）

**① 反馈表 + 接口**

`POST /api/v1/feedback`
```json
{"request_id": "800a1f3c9d24", "msg_id": "m_7f2a",
 "label": "down", "scope": "fact", "fact_id": "F117",
 "options": ["数字不对", "来源不可信", "没有回答我的问题"],
 "note": "分部占比跟年报对不上",
 "model": "deepseek-v4-flash", "prompt_version": "p3"}
```

落库 `data/feedback.db`，表 `feedback(id, ts, request_id, msg_id, label, scope, fact_id, options_json, note, model, prompt_version, git_sha)`。
`request_id` / `msg_id` 是与现有 `audit.db`、`memory.db` 关联的唯一钥匙——**这两个字段不存在，反馈就是孤儿数据**。

**② UI 采集点**（按约束，UI 改动需先提交审核）
- `ui/pages/chat.py`：每条助手消息下方一行 👍 / 👎 + 「哪里不对」三选一 + 自由文本
- `ui/pages/research.py`：报告底部一行「这份报告有用吗」+ 选中段落可报「这个数不对」
- 不新增页面，只加组件

**③ 版本戳**

`audit_log` / `conversations` / `feedback` 三处补齐 `model`、`prompt_version`、`git_sha`。没有版本戳，飞轮转了也无法归因是「哪个版本变好了」——这是飞轮能不能形成闭环的分水岭。

**④ 采样入箱（不自动进回归集）**

👎 记录 → `data/flywheel/inbox.jsonl`（待审队列）。
**人工审阅后才 promote** 到 L3 回归集。不自动进——否则一个用户误操作就把错误答案固化成了金标准，飞轮会自我污染。

**⑤ 护栏指标进 `/api/v1/metrics`**

新增 5 个：`grounding_rate`、`degraded_rate`、`llm_error_rate`、`feedback_negative_rate`、`feedback_coverage`（有反馈的回复 / 全部回复）。
前三个是**质量护栏**，后两个是**飞轮健康度**。

**⑥ 诚实边界（写进文档，也写进 UI 说明）**

本机单用户，日活以个位数计。这个飞轮能演示**闭环机制**，但样本量不足以支撑任何统计显著的改进结论。说成「数据飞轮已跑通闭环」可以，说成「飞轮带来了 X% 提升」就是编造。

### 3.4 W4｜PRD：`docs/PRD_SIA_v2.md`

现有 6 份「计划书」是工程实施计划（做了什么、怎么实现），不是产品需求文档（为谁做、解决什么问题、怎么算成功）。缺的是后者。

#### 结构

| 章节 | 要点 |
|---|---|
| 1 背景与问题 | 六大缺口（引用 §1.2），明确「本次不是加功能，是加可信度」 |
| 2 用户与场景 | 使用者画像、典型一天、当前痛点 |
| 3 范围与非目标 | 明确不做多用户/权限/部署/移动端 |
| 4 功能需求 | **每条带验收标准，且必须挂钩 L0–L4 某一层** |
| 5 非功能需求 | 延迟预算用真实数字（A股评分 ~34s、深度研究 ~140–160s）、成本结构、可用性 |
| 6 指标体系 | 北极星（有效研究产出数）+ 5 个护栏（对应 §3.3⑤） |
| 7 数据与埋点 | 最小字段集、隐私边界、留存 |
| 8 风险与降级 | 三处降级行为的处理策略、外部数据源失效路径 |
| 9 发布计划 | 分阶段，每阶段对应一个可验证的验收项 |

#### 关键设计：PRD 与评测咬合

每条功能需求写成这个形式：

> **FR-3 报告数字可溯源**
> 用户可在报告中定位到任一数字的出处与期间。
> 验收：L1 接地率 = 1.0；L0 `unknown` 分类数 = 0；台账中 `imputed` 事实在报告「数据说明」区块 100% 出现。

这样 PRD 不是文档摆设，而是评测的目录。反过来，任何一条 L 层断言若找不到对应的需求编号，说明需求写漏了。

## 五、验证标准

新交付物必须**不降低**现有质量：

1. **不回归**：`scripts/` 下 36 个 `verify_*`、11 个 `smoke_*`、`test_e2e` 现状全部保持通过（需要真实后端/网络的按现状标注 ENV 跳过）
2. **新增**：`verify_trust.py`（台账闭合 / 接地 / 降级显式化 / 插补可追溯）
3. **新增**：`verify_feedback.py`（反馈落库 / request_id 关联 / 版本戳完整）
4. **新增**：`run_eval.py --tier l0,l1,l2,l3 --baseline` 全绿，且 `data/eval/latest.json` 生成
5. **数据真实性**：本方案中出现的所有数字均为代码核查或真实运行所得；未核实的写「未核实」，不写估计值
6. **红线自检**：文档与代码中不得出现未经验证的性能数字、模型跑分、外部服务的价格承诺

| 引入 CI（GitHub Actions 等） | 无 CI 环境、且 L4 需要真实 API key；改用 `run_eval.py --tier l0-l3` 作本地门禁 |

| 多用户 / 权限 / 部署 / 移动端 | 超出范围，PRD 明确列为非目标 |
| 自动把用户反馈投入回归集 | 会自我污染金标准，必须人工过审 |
| 声称飞轮带来量化提升 | 单用户样本量不支持任何统计结论 |

## 九、这份方案对你求职的实际价值

不为凑字数而说。这四条是面试里能立刻区分候选人的点：

1. **「你的评测覆盖到研究结论了吗？」** —— 多数人只有意图分类和检索。你能答五层，且说得出「我的 L1 接地检查带反向控制，能抓出伪造的 99.99%」。
2. **「你怎么知道报告里的数字不是编的？」** —— 你不用讲「我提示词写得好」，而是「每个数字都有 `fact_id` 和出处，模型产出的字段被单独标记并做接地校验」。
3. **「数据飞轮怎么转？」** —— 你能画出五环，并指出自己的断点在「采集不可得」，且已经补上了反馈采集 + 版本戳 + 人工过审闸门。**能说出自己的断点，比说飞轮很顺更有说服力**。
4. **「PRD 怎么写 AI 产品？」** —— 你的 PRD 每条需求挂着一个可执行的评测断言。这是 AI PM 与普通 PM 的正分水岭。

同时这一版也会**修掉**你现在叙述里最容易被拆穿的一处：把「所有数字都是代码计算的」这个不成立的说法，改成「财务与估值指标为确定性计算，分部占比与情绪分为模型产出、已单独标记并做接地校验」——这更弱，但更真。
